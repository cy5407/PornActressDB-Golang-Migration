# 專案程式碼巡檢 Automation 規範

本文件整理「專案程式碼巡檢」automation 的完整執行規則，供後續維護、調整 prompt 與人工執行時對照使用。

## 1. 目標

檢查此專案程式碼是否有以下問題：

1. 資安層面或安全性問題
2. 程式碼冗餘或一致性衝突問題
3. 程式碼低效且有明顯可優化寫法的問題

## 2. 巡檢前置作業

- 每次執行時，先讀取既有報告、automation memory 與最近提交紀錄，避免重複回報已修復事項。
- 直接在既有專案工作目錄執行，不要建立 worktree。
- 將新發現、已驗證結果、已修正問題、仍待追蹤問題整理到 `security_reports` 內可持續追蹤的報告檔。
- 所有新增或更新的報告檔一律使用 UTF-8 編碼寫入；在 Windows 環境優先使用 UTF-8 with BOM，避免中文亂碼。

## 3. Worktree 與 Branch 規則

- 本 automation 預設禁止建立新的 worktree。
- 若本次僅巡檢、只更新報告、或尚未進行安全可提交的程式碼修正，直接在目前工作樹處理，不要建立新 branch。
- 只有在需要修改程式碼，且修正範圍明確、驗證可執行時，才使用固定 branch `codex/automation-review`。
- 若 `codex/automation-review` 已存在，先切換到該 branch，延續先前未完成工作。
- 若 `codex/automation-review` 不存在，才建立它。
- 不要建立其他名稱的新 branch。
- 若目前工作樹已有使用者未提交變更，且會影響修補安全性，先停止修改程式碼，改為只更新報告並明確記錄阻塞原因。
- 若目前工作樹處於 detached HEAD，且本次只做巡檢或只更新報告，維持現狀，不主動切 branch。
- 若本次需要修改程式碼，才切換到 `codex/automation-review`。
- 若切換 branch 可能覆蓋或干擾現有未提交變更，停止修碼，改為只更新報告並記錄原因。

## 4. 修碼策略

- 先以高信噪比巡檢為主，只處理可證明、可行動、風險可控的問題。
- 若問題明確、修正範圍小、且能完成必要驗證，優先直接修正。
- 若沒有安全可提交的程式碼變更，則只更新報告，不修改程式碼。
- 不要為了清理低價值問題而做大範圍重構。

## 5. 有程式碼變更時的最低完成門檻

若本次有修改任何程式碼，完成後不得只停留在靜態檢查或定向單元測試；至少必須完成以下驗證後，才可視為完成：

### 5.1 建置驗證

- Python GUI 相關變更：必須成功建置 Windows GUI 發行檔，例如：
  - `python -m PyInstaller --clean --noconfirm "女優分類系統_修復版.spec"`
- Go 相關變更：必須成功建置 `classifier.exe`，例如：
  - `go build -o classifier.exe .\cmd\scanner`
- 若 GUI 發行版依賴 `classifier.exe`，必須同步將最新 `classifier.exe` 複製到 `dist`。

### 5.2 啟動與功能 smoke test

- GUI 相關變更：必須實際啟動 GUI exe，確認程式不會立即崩潰，並至少驗證一次主視窗可正常建立。
- Go / 橋接相關變更：必須至少執行一個實際命令確認功能可用，例如：
  - `classifier.exe help`
  - `classifier.exe scan ...`
  - `classifier.exe db stats`
- 若修改的是特定功能，必須再執行至少一個與該功能直接相關的 smoke test，不能只做無關的啟動測試。

### 5.3 測試與語法檢查

- 必須執行與修改內容直接相關的 targeted tests。
- 至少執行變更檔案的語法檢查，例如：
  - `python -m py_compile ...`
  - `go test ...`

## 6. 完成定義

- 只有在 build 成功、程式可啟動、相關 smoke test 通過後，才可視為本次修復完成。
- 若因環境限制無法完成其中任一步驟，不可標示為完成；必須在報告中明確記錄：
  - 哪一步沒做
  - 為什麼沒做
  - 目前風險
  - 下一步需要什麼條件

## 7. 報告要求

- 每次有程式碼修改時，報告內必須明列：
  - build 指令
  - smoke test 指令
  - targeted test 指令
  - 驗證結果
  - 產物位置，例如 `dist\女優分類系統_修復版.exe`
  - 本次使用的 branch
- 若本次沒有修改程式碼，也要明確記錄：
  - 本輪僅巡檢 / 僅更新報告
  - 沒有安全可提交修正的原因
  - 仍待追蹤的問題

## 邏輯檢查結論

這 7 點整理後沒有邏輯衝突，執行順序如下：

1. 先做巡檢前置作業
2. 判斷本輪是否只巡檢或要修碼
3. 只有修碼時才進入 branch 規則
4. 只有修碼時才需要滿足 build、smoke test、targeted tests
5. 最後統一回寫追蹤報告

這樣可以避免以下常見衝突：

- 只更新報告卻被要求切 branch
- 尚未修碼卻被要求 build
- 修碼完成卻只做靜態檢查就宣告完成
- detached HEAD 狀態下，巡檢流程被強迫切 branch 打亂現場
